Known vulnerabilities

Every vulnerability known in RCP For All Camera and its dependencies, what was done about it, and the test that proves it stays fixed.

At a glance

RCP For All Camera is a desktop application. It opens no network port: it drives a USB control panel and reaches cameras on the production network. What it must protect is the camera passwords and the control of live equipment (recording, colour bars, tally).

How vulnerabilities are found

Two kinds of vulnerability matter: those in code the project depends on, and those in the project's own design.

Dependencies

govulncheck, the Go team's scanner, compares the exact versions the application is built with against the Go vulnerability database. It reports a vulnerability only when the application actually calls the affected code i. It runs:

  • on every push to main and every pull request, in the CI workflow (.github/workflows/ci.yml);
  • every Monday at 06:00 UTC, in .github/workflows/vulncheck.yml, because new vulnerabilities are published for code that has not changed. It can also be started by hand from the Actions tab.

To run the same check on your machine:

go run golang.org/x/vuln/cmd/govulncheck@v1.1.4 ./...

When the weekly check fails: read the report, upgrade the module named in Fixed in (go get module@version, or the toolchain line of go.mod for the standard library), run the tests, then add the entry to the table below.

The application's own design

The threats come from the threat model: what crosses into the application from the disk, the USB panel, the network and the camera modules. Each protection has a test that attacks it; the threats table names them. They run with every go test ./..., on every push.

More info: why a desktop app cares about HTTP/2 and image bugs

The application talks HTTP to the cameras, and the Go HTTP client negotiates HTTP/2 when a server offers it. A device on the production network that pretends to be a camera could send crafted answers, so the client code is exposed even though the application serves nothing. x/image comes with the Fyne interface toolkit, which decodes the application's own icons and images.

The proof that these are fixed is the scan itself: govulncheck on the current go.mod reports no vulnerability, in CI on every push to main and every week.

Application threats

What an attacker, a faulty device or a broken file could try, and the test that proves it does not work. Test names are Go test functions; run one with go test ./internal/<package> -run <TestName>.

Camera modules

More info: what is out of reach

Malware running as the same Windows user, and local administrators, can read the process memory and decrypt the secrets file as the user: no desktop application can defend against them. On Windows, Go ignores the 0600 file mode, so the files rely on the per-user %APPDATA% folder permissions. The full list of residual risks is in the security model.

Reporting a vulnerability

Found a way around one of these protections, or a vulnerability not listed here? Please report it privately with Report a vulnerability under the Security tab of the GitHub repository, not in a public issue. Describe what you did, what happened and the version you used.

Every confirmed report gets a row in this page, with the test that proves the fix.
