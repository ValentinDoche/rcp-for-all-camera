RCP For All Camera

One USB control panel and one desktop application to shade every camera of a production, whatever its brand.

What the application does

A camera operator shades cameras (iris, gain, shutter, white balance, colour) from a remote control panel, an RCP. Each brand sells its own, and Blackmagic's ATEM Micro Camera Panel normally needs an ATEM switcher. RCP For All Camera drives that panel directly over USB from a Windows PC and controls the cameras over the network, so one panel serves Blackmagic, Sony and Panasonic cameras side by side.

A real control panel

The ATEM Micro Camera Panel's buttons, knobs, iris lever, displays and lights, with no ATEM switcher.

A desktop window

Eight camera strips, a details page per camera, presets and settings, in English or French, light or dark.

Camera modules

Each camera model is a module file in the modules folder. Add a camera by adding a file.

Status of 0.3.0-ALPHA. The panel and the window work. The Blackmagic Studio Camera 6K Pro is controlled over the network; the demo camera simulates one. The other models (Blackmagic Pocket and Studio, Sony FX3, FX6, FX9, FR7, Panasonic AW-UE100/150/160) declare their controls but do not talk to the camera yet. Routing a camera to a Videohub, ATEM or vMix output is not started.

Quick start

  1. Get the application. Download the zip of the latest release from the GitHub releases and unzip it. It holds rcp.exe and the modules folder. To build it yourself, see Build from source.
  2. Close ATEM Software Control if it runs: it also drives the panel and would overwrite its displays.
  3. Plug in the panel and start rcp.exe. The title bar says Micro Camera Panel active. No panel at hand? Start rcp.exe -sim, or click the panel status and choose Simulator: an on-screen panel replaces the real one. i
  4. Assign a camera. Click Assign a camera on a free strip, choose the brand and model, enter its address. Pick Demo to try everything without a camera.
  5. Shade. Press the panel's camera button, move the iris lever, turn the knobs. The window and the panel follow each other.

Key concepts

Slot
One of the eight camera positions, matching the panel's camera buttons 1 to 8. The active slot is the one the panel controls.
Rig
The eight slots and the camera assigned to each: model, name, address. Saved in rig.json.
Control
One adjustable setting of a camera: iris, gain, white balance, lift red... Each has an id, a kind (range, choice, on/off, action, text) and limits. The panel and the window work only with controls.
Module
The program that teaches the application one camera model. It translates controls into the camera's protocol. See Camera modules.
Preset
A snapshot of a camera's control values, stored by the application under a number (1 to 5) and written back on recall. Presets stay on the PC, never on the camera.
Operator lock
Sensitive controls (record, colour bars) ask for confirmation before they are sent. On by default.
Soft takeover
After a camera switch, the iris lever and the master black ring take control only once they reach the camera's current value, so the picture never jumps.

Architecture

The application is one Go program, rcp.exe, plus one WebAssembly file per camera model. Inside, the code is split into layers, and dependencies only point inwards: the core knows nothing of the window, the panel, the disk or the network.

PackageRole
internal/coreThe language every part shares: control descriptions, values, events, camera models, page layouts. Depends on nothing.
internal/appThe use cases: assign a slot, set a control, store or recall a preset, change a setting. Declares the ports it needs (storage, secrets, panel).
internal/pluginsLoads the modules folder and runs each module in a WebAssembly sandbox. Checks everything a module says.
internal/configrig.json and the encrypted secrets file.
internal/guiThe native window (Fyne).
internal/surfaces/panel, panelmodelThe panel controller and its pure model: what the panel shows, what each key and knob does.
internal/surfaces/micropanelThe USB HID driver of the ATEM Micro Camera Panel (Windows).
internal/surfaces/panelsim, panelsourceThe on-screen panel simulator, and the choice between USB panels and the simulator.
sdk/rcpmodThe library a module is written with. See Camera modules.
cmd/rcpBuilds every part and wires them together. Nothing else.
More info: how the rules are enforced

A test, internal/archtest/dependency_rules_test.go, reads the imports of every package and fails when one breaks the rules: core imports no other package of the project, nor the network or the GUI toolkit; app imports no adapter; a module imports nothing but the SDK. The rules themselves are in Go engineering rules.

From the panel to the camera

What happens when the operator pushes the iris lever:

  1. The panel sends a USB report with the lever position. The driver authenticates the panel and decodes the report.
  2. The panel controller turns the position into an f-stop of the active camera, within the lens' limits and the window set by the COARSE and SENS knobs, and checks soft takeover.
  3. It calls the application: set control iris of slot 2 to f/5.6. The application checks the value against the camera's declared limits and the operator lock.
  4. The application hands the value to the camera's module, which sends it in the camera's own protocol (for the Studio 6K Pro, an HTTP request to its REST API).
  5. The camera confirms with an event. The application forwards it to the window and the panel, which update their displays. If the command fails, the panel's ALARM light blinks and the window shows a notice.

Writes are throttled per control: moving the lever fast sends about 30 values per second at most, and always the final one.

The control panel

The panel works like a broadcast RCP. The main controls:

ControlWhat it does
CAMERA 1–8Select the active camera. Blue: assigned; orange: active; red: on air (tally).
Iris leverIris, over the lens' range, with soft takeover. COARSE and SENS narrow its travel to a window of f-stops.
Master black ringMaster black, with a small dead zone at the centre.
WHITE / BLACK R G B knobsColour gain and lift of each channel.
ND, GAIN, SHUTTER ▲▼Step the ND filter, the gain (or ISO) and the shutter.
W/BShort press: white balance mode (GAIN sets tint, SHUTTER the Kelvin). Long press: auto white balance.
STORE, SCENE 1–5Presets: STORE then a number stores; a number alone recalls.
BARSColour bars on or off (asks for confirmation while the operator lock is on).
PANEL ACTIVETurns panel control off and on.

The displays show the active camera's ND, gain, shutter, iris and master black: blank when the camera has no such control, dashes when its value is unknown. Every key, light and display is described in the panel mapping; the USB protocol in Panel USB protocol.

The application window

Cameras

One strip per slot: the colour wheel (lift, gamma, gain), the iris pad (iris up and down, master black left and right), zoom and focus, the ND, gain, shutter and white balance readouts, and quick actions (auto focus, auto iris, auto white balance). What a camera does not have is greyed out, so every strip looks the same. The tabs above select the active camera, like the panel's buttons.

Details

Details on a strip opens every control of that camera: exposure and lens cards, presets, colour wheels, then every other setting. The camera's module decides the layout in its ui.go (The UI file).

Settings

The gear at the bottom left opens Settings:

  • General: language, theme, system statistics in the bottom bar, the network adapter used to reach the cameras, start with Windows, the operator lock, the log level, export and import of the configuration.
  • Cameras: assign, edit or remove the camera of each slot.
  • Panel: which panel to drive (first USB panel, a given one by serial number, or the simulator).
  • About: version, author, licences.

Data and security

WhatWhere
The rig, presets and settings%APPDATA%\RCPForAllCamera\rig.json
Camera passwords, encrypted for the Windows user (DPAPI)%APPDATA%\RCPForAllCamera\secrets.dat
Logsrcp.log, opened from Settings › General › Logs
Compiled modules cache%LOCALAPPDATA%\RCPForAllCamera\modules

Passwords never reach rig.json, an exported file, a log or the screen. Modules run in a sandbox that can reach only their own camera. Every file and every message from a module or the panel is checked before use. The list of known vulnerabilities, and the test that proves each protection, is on the Known vulnerabilities page.

Build from source

You need Go 1.27 or later and, because the window toolkit uses cgo, a C compiler (MinGW-w64 on Windows).

winget install BrechtSanders.WinLibs.POSIX.UCRT
go build -ldflags "-H windowsgui" -o rcp.exe ./cmd/rcp
go run ./cmd/buildmodules -o modules

The first command installs the compiler, the second builds the application (the first build takes a few minutes), the third compiles every module of modules/ into the modules folder next to rcp.exe.

CommandUse
rcp.exe -simStart on the panel simulator (this run only).
rcp.exe -modules <folder>Load the modules from another folder.
go run ./cmd/buildmodules -o out demoBuild only the named modules.
go run ./cmd/panelcheck -t 60sShow a fake rig on a real panel.
go run ./cmd/panelprobe -t 10sAuthenticate the panel and dump its USB reports.
More info: releases

Pushing a tag such as v0.3.0-ALPHA runs the release workflow: tests, build of rcp.exe and of every module, a zip with the README, and a GitHub release (a tag with a suffix is a pre-release).

Tests and quality

go test ./...
go test -race ./internal/...

The tests need no hardware and no network. What they cover:

  • Every package from the outside. Tests use a package's public API only, so they keep passing when the inside changes.
  • The window like a user. GUI tests find a text or a widget on screen, click it and read the window again (internal/gui/ui_driver_test.go).
  • The panel on a virtual clock. Blinking lights, long presses and timeouts are tested with testing/synctest, without waiting.
  • Every module against the same contract, offline and connected to a fake camera.
  • The sandbox against a hostile module written to escape it.
  • The architecture, by the dependency rules test.

The CI runs gofmt, go vet, the tests with the race detector and govulncheck on every push to main and every pull request. Tests against real cameras run only when asked: BMD_CAMERA=<ip> go test ./internal/plugins -run Live -v.
