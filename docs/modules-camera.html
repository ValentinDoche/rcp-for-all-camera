Caméras · 0.3.0-ALPHA

Modules caméra

Ajouter une caméra en déposant un fichier dans le dossier modules, sans toucher à l'application.

L'essentiel

Chaque modèle de caméra est un module : un petit fichier .wasm que l'application charge au démarrage. Il traduit la langue commune de l'application dans le protocole de sa caméra, et il tourne enfermé dans un bac à sable.

Comment ça marche

Un fichier par caméra dans modules\, une langue commune, un traducteur par modèle.

Le contrat

Ce qu'un module fournit et ce que l'application lui prête : le réseau vers sa caméra, des minuteries, des événements.

Exemple : le module demo

Une caméra simulée, complète, pas à pas. Le meilleur modèle à recopier.

Familles et hooks

Une base partagée par marque (bm pour Blackmagic), et des hooks pour ce qui est propre à un modèle.

Le bac à sable

Un module ne voit ni vos fichiers ni Internet : seulement l'adresse de sa caméra.

Vérifier un module

Une suite de contrat, la même pour tous les modules, sans caméra branchée.

L'idée en une image

Chaque marque de caméra a sa propre « langue » : Blackmagic se pilote par des requêtes web, Sony par son interface distante, Panasonic par des commandes CGI. L'application, elle, ne parle qu'une langue : « mets l'iris à f/4 », « le gain à 6 dB », « préviens-moi quand la balance des blancs change ».

Un module caméra est un traducteur entre les deux. Il est livré sous la forme d'un fichier .wasm (WebAssembly, un format de programme portable) rangé dans le dossier modules. Au démarrage, l'application ouvre ce dossier et charge chaque fichier qu'elle y trouve. Pour ajouter une caméra, on ajoute un fichier ; pour en retirer une, on l'enlève.

À retenir. Le panneau, l'interface, les presets et les réglages ne savent pas quelle marque ils pilotent. Toute la connaissance d'une caméra est dans son module, et un module ne peut rien faire d'autre que parler à sa caméra.

Les mots à connaître

Module
Le code qui pilote un modèle de caméra, livré dans un fichier <identifiant>.wasm.
Identifiant de module
Des mots en minuscules séparés par des tirets, en commençant par la marque : bm-studio-6k-pro, sony-fx6, panasonic-aw-ue150, demo. Le fichier porte ce nom. L'identifiant est enregistré dans rig.json, donc il ne change plus une fois publié (voir les alias).
WebAssembly (.wasm)
Un format de programme portable et enfermé : le même fichier marche sous Windows, macOS et Linux, et il ne peut rien faire que l'application ne lui permette. On l'écrit en Go (ou en Rust, ou dans un autre langage).
SDK rcpmod
La boîte à outils pour écrire un module en Go (dossier sdk/rcpmod) : les types du contrat, les outils pour décrire les réglages, et le branchement avec l'application.
Hôte
L'application vue par le module. Elle lui prête des fonctions : envoyer une requête à sa caméra, ouvrir une connexion WebSocket vers elle, programmer une minuterie, publier un événement, écrire au journal.
Réglage (control) et fiche (ControlSpec)
Un paramètre de la caméra (iris, gain, lift rouge…) et sa description : type (plage, liste, interrupteur, action), limites, unité. L'interface dessine ses curseurs à partir des fiches : un nouveau réglage n'exige aucune modification de l'interface.
Valeur et événement
Une valeur se lit ou s'écrit (Number(4), Choice("400"), Bool(true), Trigger()). Un événement est ce que la caméra signale d'elle-même : « l'iris est passé à f/5.6 », « je suis connectée », « l'objectif a changé ».
Base partagée et hook
Le code commun à une famille de caméras qui parlent le même protocole (bm pour Blackmagic), et les points d'entrée où un module remplace un comportement de la base par le sien.

Un module dont le fichier ne porte pas le nom de son identifiant, dont la fiche est mal formée ou qui ne répond pas est écarté au démarrage : il est signalé dans le journal, et les autres modules se chargent normalement.

Le contrat d'un module

Le contrat est la liste de ce que l'application attend d'un module. Si un module le respecte, il fonctionne avec tout le reste : le panneau, l'interface, les presets, la sauvegarde. En Go, il s'écrit avec le SDK rcpmod.

Ce que le module fournit

// Module est le code qui pilote un modèle de caméra.
type Module interface {
    Info() Info                                     // sa fiche : identifiant, marque, nom, port…
    New(cfg Config, host Host) (Camera, error)      // une caméra pour cette saisie
}

// Camera est une caméra configurée.
type Camera interface {
    Controls() []ControlSpec                 // ses réglages, sans connexion
    Connect() error                          // commence à se connecter
    Close()                                  // coupe tout
    Get(id string) (Value, error)            // lit un réglage
    Set(id string, v Value) error            // écrit un réglage
}

Ce que l'application prête au module

// Host est l'application vue par le module.
type Host interface {
    HTTP(method, path string, body []byte) (status int, resp []byte, err error)  // vers SA caméra
    OpenWebSocket(path string, onMessage func([]byte), onClose func(error)) (WebSocket, error)
    After(d time.Duration, fn func()) (cancel func())   // une minuterie
    Emit(e Event)                                       // un événement vers l'application
    Log(level Level, msg string)                        // le journal de l'application
}

Le module ne donne jamais d'adresse : HTTP("PUT", "/control/api/v1/lens/iris", …) part toujours vers l'adresse et le port que l'utilisateur a saisis pour cette caméra. C'est ce qui rend le bac à sable possible.

Les règles du contrat

RèglePourquoi
Controls() ne demande aucune connexion et ne change pas.L'interface dessine la page d'une caméra même éteinte.
Set vérifie la valeur avant tout envoi.Une valeur invalide n'atteint jamais la caméra. L'application la vérifie aussi avant d'appeler le module : deux lignes de défense.
Connect lance la connexion et la caméra annonce son état par un événement Status.L'application attend ce premier état pour savoir si la caméra répond. Ensuite, le module se reconnecte tout seul (avec une minuterie) jusqu'à Close.
Le module publie chaque changement par Emit.L'interface et le panneau affichent ce que la caméra a vraiment fait, pas ce qu'on lui a demandé.
Les erreurs sont celles du SDK : ErrUnknownControl, ErrInvalidValue, ErrReadOnly, ErrNotConnected, ErrNotImplemented.L'interface sait les afficher sans connaître la marque. Toute autre erreur devient « erreur interne ».

Un module ne s'exécute jamais en même temps que lui-même. L'application lui passe les appels un par un : un geste sur le panneau, un message de la caméra, une minuterie. Pas de verrou ni de goroutine à gérer dans un module : on écrit du code simple, qui réagit aux événements.

La vie d'une caméra

  1. Au démarrage, l'application scanne le dossier modules, charge chaque fichier, lit sa fiche et la vérifie. Un module mal formé est écarté et signalé dans le journal.
  2. L'utilisateur ajoute une caméra sur le bouton 1 en choisissant « Caméra de démonstration ». L'application vérifie la saisie, puis crée une instance du module rien que pour cette caméra : deux caméras du même modèle ne partagent rien.
  3. L'application se connecte. Le module annonce « connectée » : la pastille passe au vert.
  4. L'utilisateur demande f/1.4. L'application vérifie que la valeur est dans les limites déclarées, puis la transmet au module. L'objectif simulé ne descend pas sous f/2.8.
  5. Le module publie la valeur réelle (f/2.8). L'interface et le panneau affichent ce que la caméra a vraiment fait.

Exemple : le module demo

Le module demo (dossier modules/demo) simule une caméra de studio avec un zoom 24-70 mm f/2.8. Il n'a pas d'adresse réseau : il sert à essayer l'interface et le panneau sans caméra.

Étape 1 : le programme et la fiche

package main

import "github.com/valentindoche/rcp-for-all-camera/sdk/rcpmod"

// main reste vide : le SDK branche le module sur l'application.
func main() {}

func init() { rcpmod.Register(module{}) }

type module struct{}

func (module) Info() rcpmod.Info {
    return rcpmod.Info{
        ID: "demo", Brand: "Démo", Name: "Caméra de démonstration",
        Transports: []string{rcpmod.TransportEthernet},
        Auth:       rcpmod.AuthNone,        // pas de mot de passe
        Support:    rcpmod.SupportSupported,
        NoAddress:  true,                  // pas d'adresse à saisir
        InterchangeableLens: true,         // la case « zoom motorisé » est proposée
        Aliases:    []string{"demo.camera"}, // ancien identifiant (0.2.x)
    }
}

Étape 2 : les réglages

Chaque réglage est une fiche. Le nom standard (rcpmod.Iris, rcpmod.Gain…) suffit : l'application y ajoute le libellé et la rubrique affichés à l'écran.

func specs() []rcpmod.ControlSpec {
    return []rcpmod.ControlSpec{
        rcpmod.Range(rcpmod.Iris, 1, 22, 0.1, "f"),          // une plage, de f/1 à f/22
        rcpmod.Action(rcpmod.AutoIris),                         // un bouton « auto »
        rcpmod.Range(rcpmod.Gain, -12, 36, 2, "dB"),          // pas de 2 dB
        rcpmod.Enum(rcpmod.ISO, rcpmod.Opts("400", "800", "1600")),   // une liste
        rcpmod.Toggle(rcpmod.Record),                           // un interrupteur
        // … et une quarantaine d'autres
    }
}

Étape 3 : la caméra

type camera struct {
    host  rcpmod.Host
    specs rcpmod.Specs                        // retrouve et vérifie les fiches
    on    bool
    vals  map[string]rcpmod.Value
}

func (module) New(cfg rcpmod.Config, host rcpmod.Host) (rcpmod.Camera, error) {
    s := rcpmod.NewSpecs(specs())
    if !cfg.PowerZoom {
        s = s.Without(rcpmod.Zoom)             // pas de zoom sans objectif motorisé
    }
    return &camera{host: host, specs: s, vals: initial()}, nil
}

// Connect réussit tout de suite : il n'y a rien à joindre.
func (c *camera) Connect() error {
    c.on = true
    c.host.Emit(rcpmod.StatusEvent(rcpmod.StateConnected, ""))
    return nil
}

// Set vérifie la valeur, l'applique comme une vraie caméra, publie les changements.
func (c *camera) Set(id string, v rcpmod.Value) error {
    if _, err := c.specs.Validate(id, v); err != nil {
        return err
    }
    if !c.on {
        return rcpmod.ErrNotConnected
    }
    for _, e := range c.apply(id, v) {     // l'iris reste dans l'objectif, etc.
        c.host.Emit(e)
    }
    return nil
}

Comme une vraie caméra. Le module demo applique les conséquences d'un réglage : l'iris reste entre f/2.8 et f/22, la vitesse d'obturation et l'angle se suivent, le noir (master black) est le lift de luminance, la balance automatique s'arrête sur 5600 K. Ce qui marche sur la démo marche sur une vraie caméra.

Construire et installer

  1. Construire tous les modules : l'outil scanne modules/ et compile chaque dossier. 
    go run ./cmd/buildmodules -o dist/modules
    Pour un seul module : go run ./cmd/buildmodules -o dist/modules demo. Sous le capot, c'est GOOS=wasip1 GOARCH=wasm go build -buildmode=c-shared.
  2. Installer : copier demo.wasm dans le dossier modules à côté de rcp.exe (l'installeur le fait pour les modules fournis).
  3. Relancer l'application : le modèle apparaît dans la liste des caméras.

Pour développer, rcp.exe -modules dist\modules charge un autre dossier.

Vérifier un module

Un module se teste comme n'importe quel code Go, sans WebAssembly et sans caméra, grâce à un hôte de test (sdk/rcpmod/rcpmodtest) qui joue le rôle de l'application : il enregistre les requêtes du module, lui répond, déclenche les minuteries à la demande et collecte les événements.

func TestContract(t *testing.T) { rcpmodtest.Module(t, module{}) }

func TestIrisStaysInsideTheLens(t *testing.T) {
    host := rcpmodtest.NewHost()
    cam := host.Connected(t, module{}, rcpmod.Config{Model: "demo"})
    _ = cam.Set(rcpmod.Iris, rcpmod.Number(1.4))
    if got := host.Last(rcpmod.Iris); got.Number != 2.8 {
        t.Errorf("iris = f/%g, want f/2.8", got.Number)
    }
}

La suite de contrat rcpmodtest.Module est la même pour tous les modules. Elle vérifie que la fiche est bien formée, que chaque réglage a une fiche valide et n'est déclaré qu'une fois, qu'une valeur du mauvais type est refusée avant tout envoi, et qu'une caméra connectée répond à chaque lecture avec une valeur du bon type.

Enfin, l'application teste le vrai fichier .wasm : elle construit le module demo, le charge comme en production et lui fait passer le contrat de l'application (cameratest). Les modules qui pilotent une vraie caméra ont aussi des tests « live », sautés par défaut, à ne lancer sur une caméra en exploitation qu'avec l'accord de son propriétaire.

Familles, base partagée et hooks

Plusieurs caméras d'une même marque parlent le même protocole : les Blackmagic Studio et Pocket récentes se pilotent toutes par la même API REST. Ce protocole est écrit une seule fois, dans la base partagée modules/internal/bm. Chaque modèle a son petit module qui s'en sert. Chaque fichier .wasm embarque sa copie de la base : les modules restent indépendants.

« Hériter » en Go : la composition

Go n'a pas d'héritage de classes. On obtient le même résultat par composition : le module construit la base en lui donnant ses réglages et, s'il le faut, ses hooks. Le module entier tient en quelques lignes :

func init() { rcpmod.Register(module{}) }

func (module) New(cfg rcpmod.Config, host rcpmod.Host) (rcpmod.Camera, error) {
    return bm.New(cfg, host, bm.Model{Specs: specs(cfg.PowerZoom)}), nil
}

// Exemple imaginaire : un firmware qui attend l'ISO dans une autre propriété.
var hooks = bm.Hooks{
    Encode: func(id string, v rcpmod.Value) (bm.Command, bool, error) {
        if id != rcpmod.ISO {
            return bm.Command{}, false, nil      // pas pour moi : la base s'en charge
        }
        return bm.Command{Path: "/video/sensitivity", Body: map[string]any{"iso": v.Choice}}, true, nil
    },
}

La Studio Camera 6K Pro n'a besoin d'aucun hook aujourd'hui. Les hooks sont là pour le prochain modèle qui différera, sans toucher au code des autres.

Le bac à sable

Un module WebAssembly ne peut rien faire seul : ni lire un fichier, ni ouvrir une connexion, ni lancer un programme. Il ne dispose que des fonctions que l'application lui prête, et l'application les limite.

LimiteEffet
Le réseau ne va qu'à l'adresse et au port saisis pour la caméra, en HTTP et WebSocket.Un module ne peut ni contacter Internet, ni scanner le réseau local, ni joindre une autre caméra.
Aucun accès aux fichiers, aux variables d'environnement, aux autres programmes.Vos documents et vos mots de passe restent hors de portée. Le mot de passe de la caméra n'est donné qu'à son module.
Mémoire plafonnée par instance, réponses et messages limités à 1 Mo, délai sur chaque appel.Un module qui boucle ou gonfle ne fige pas l'application : il est arrêté et sa caméra passe en erreur.
Un module qui plante n'arrête que sa caméra.Les autres caméras, le panneau et l'interface continuent de fonctionner.
Le dossier modules est dans Program Files.Seul un administrateur peut y déposer un module.

Sony, Panasonic et les autres

Le contrat ne dit rien de Blackmagic : il parle de réglages, de valeurs et d'événements. La recette est toujours la même :

  1. Déclarer le modèle tant que son protocole n'est pas écrit : un module « prévu » (rcpmod.Planned), avec sa fiche et ses réglages. Il apparaît dans la liste, l'interface dessine sa page, et chaque action répond « pas encore écrit ».
  2. Écrire le protocole une fois, dans une base de marque (modules/internal/sony), avec ses tests sur l'hôte de test.
  3. Brancher le module du modèle sur cette base, en gardant son identifiant (sony-fx6).
  4. Passer le contrat, puis les tests live sur la vraie caméra, avec l'accord de son propriétaire.

Les fonctions prêtées par l'hôte grandiront avec les besoins : TCP et UDP pour le protocole VISCA des caméras PTZ, par exemple. Elles garderont la même règle : seulement vers l'adresse de la caméra.

Annexe : l'ABI, pour écrire un module dans un autre langage

Le SDK Go cache ce qui suit. Un module écrit en Rust, en Zig ou en C doit le faire lui-même. Un module est un « réacteur » WASI preview 1 (il exporte _initialize). Toutes les données échangées sont du JSON en UTF-8.

SensFonctionRôle
exportéercp_alloc(len i32) → ptr i32Réserve len octets où l'hôte écrit la requête.
exportéercp_call(ptr i32, len i32) → i64Traite une requête {"op": …} ; renvoie ptr << 32 | len de la réponse, valable jusqu'à l'appel suivant.
importéercp.call(ptr i32, len i32) → i64Demande un service à l'hôte ; renvoie id << 32 | len de la réponse, gardée par l'hôte.
importéercp.take(id i32, ptr i32)Copie cette réponse à l'adresse donnée (le module a réservé len octets).
importéercp.log(level i32, ptr i32, len i32)Écrit une ligne au journal.

Requêtes de l'hôte vers le module (rcp_call)

info, new (avec config), controls, connect, close, get (id), set (id, value), wsMessage (socket, text), wsClosed (socket, error), timer (timer). Une réponse est {"result": …} ou {"error": {"code": "INVALID_VALUE", "message": …}}.

Services de l'hôte (rcp.call)

http (method, path, body), wsOpen (path), wsSend (socket, text), wsClose (socket), after (ms), cancel (timer), emit (event). La référence exacte des champs est le code du SDK : sdk/rcpmod/wire.go.

Questions fréquentes

J'avais des caméras enregistrées avant la 0.3.0. Sont-elles perdues ?

Non. Les anciens identifiants (blackmagic.studio6kpro, demo.camera…) sont déclarés comme alias dans la fiche du module. L'application les reconnaît et enregistre le nouvel identifiant à la sauvegarde suivante. Les presets suivent.

WebAssembly, ce n'est pas lent ?

Un appel au module coûte environ 10 microsecondes ; le levier d'iris du panneau envoie une valeur toutes les 50 millisecondes. La compilation d'un module (environ 0,3 s) est faite une fois puis gardée en cache.

Où mettre un réglage propre à une marque ?

Dans le module ou sa base, avec un nom préfixé par la marque (blackmagic.contrastPivot). L'interface l'affiche sans modification. Si plusieurs marques finissent par avoir le même réglage, il devient un nom standard.

Une caméra a deux façons de régler l'iris : laquelle déclarer ?

Celle que les gens voient (iris, en f-stops). Une seconde forme destinée au panneau (irisNorm, la course de l'objectif) est déclarée Hidden : le panneau s'en sert, l'interface et les presets l'ignorent.

Que se passe-t-il si un module renvoie une erreur ?

L'application la traduit en un code stable (INVALID_VALUE, NOT_CONNECTED…) que l'interface affiche et que le panneau signale par le voyant ALARM. Une erreur inattendue devient INTERNAL, sans détail technique à l'écran.
