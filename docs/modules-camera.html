Developer guide

Camera modules

Teach RCP For All Camera a new camera: write a module, build it, drop one file in the modules folder.

Overview

A camera module is a small program that controls one camera model. The application loads every module it finds in its modules folder and talks to it in one common language: controls, values and events. The module translates that language into the camera's own protocol.

How modules work

Every camera brand speaks its own protocol: one camera takes REST requests, another a vendor remote protocol, a third CGI commands. The application never deals with them. It only knows controls ("iris", "gain", "white balance"), values (f/4, 6 dB, 5600 K) and events ("the iris is now f/5.6").

A module bridges the two. It is delivered as one WebAssembly file, <id>.wasm i, in the modules folder next to rcp.exe. The application loads every file of that folder when it starts. To add a camera model, you add a file; to remove one, you delete it.

Key idea. The control panel, the window, presets and settings never know which brand they drive. Everything about a camera lives in its module, and a module can do nothing but talk to its camera.

Key concepts

Module
The code that controls one camera model, delivered as <id>.wasm. Every module is self-contained: it shares no code with other modules.
Module id
Lowercase words joined by single hyphens, starting with the brand: bm-studio-6k-pro, sony-fx6, demo. The file is named after it. The id is saved with each configured camera, so keep it stable once published.
Camera
One configured camera: a module plus what the user entered (name, address, port, credentials). Each camera runs in its own instance of the module.
Control
One camera parameter: iris, gain, lift red, record… A control has an id. Standard ids (iris, gain) let the panel and the window treat every camera alike.
Control description (ControlSpec)
What a control is: its kind (range, choice list, on/off, action, text), limits, unit and options. The window draws its widgets from these descriptions: a new control needs no change in the application.
Value and event
A value is what you read or write (Number(4), Choice("400")). An event is what the camera reports by itself: a new value, a connection state, new lens information.
Host
The application, as a module sees it. It lends the module a few services: HTTP and WebSocket to its own camera, timers, events and logging.
SDK rcpmod
The Go package for writing modules: the contract types, the helpers that describe controls, and the plumbing that connects a module to the application.

Quick start

You need the project's source code and Go (the version in go.mod; the go command downloads the right toolchain by itself). No camera is required.

  1. Copy the demo module. It is a complete, simulated camera. 
    cp -r modules/demo modules/acme-cam
  2. Give it its own id and name. In modules/acme-cam/main.go, change Info(): 
    ID: "acme-cam", Brand: "Acme", Name: "Cam 1",
    The folder name and the id must match. ui.go, next to it, lays out the camera page: keep the demo's, or return rcpmod.StandardPage().
  3. Build it. 
    go run ./cmd/buildmodules -o dist/modules acme-cam
    This writes dist/modules/acme-cam.wasm.
  4. Run the application with it. Either copy the file into the modules folder next to rcp.exe, or point the application at the build folder: 
    rcp.exe -modules dist\modules
  5. Add the camera. In the application, assign "Acme Cam 1" to a camera button. Its page shows every control the module declares.
More info: where modules live

In the source tree, modules/ holds one folder per module, each with a main.go. The build tool compiles every folder it finds (except internal) to <folder>.wasm; give it folder names to build only those. Under the hood it runs GOOS=wasip1 GOARCH=wasm go build -buildmode=c-shared.

An installed application keeps its modules in C:\Program Files\RCP For All Camera\modules\, where only an administrator can write. When it starts, the application compiles each file once and keeps the result in a cache (%LOCALAPPDATA%\RCPForAllCamera\modules), so later starts are fast.

A file is skipped, with a line in the application log, when it is not a valid module, when its declaration is malformed, or when its name differs from its module id. The other modules still load.

The module contract

A module implements two interfaces from the SDK. The application calls them; the module answers.

// Module controls one camera model.
type Module interface {
    Info() Info                                  // the model declaration
    New(cfg Config, host Host) (Camera, error)   // one camera for what the user entered
}

// Camera is one configured camera.
type Camera interface {
    Controls() []ControlSpec            // its controls, without connecting
    Connect() error                     // start connecting
    Close()                             // stop everything
    Get(id string) (Value, error)       // read a control
    Set(id string, v Value) error       // write a control
}

The application lends each camera a Host:

type Host interface {
    HTTP(method, path string, body []byte) (status int, resp []byte, err error)
    OpenWebSocket(path string, onMessage func([]byte), onClose func(error)) (WebSocket, error)
    After(d time.Duration, fn func()) (cancel func())
    Emit(e Event)
    Log(level Level, msg string)
}

A module never names a host: HTTP("PUT", "/control/api/v1/lens/iris", body) always goes to the address and port the user entered for this camera. See Host services for the details of each call.

Rules every module follows

RuleWhy
Info() is static and well formed (id, brand, name, at least one transport).The application reads it once, when it loads the file.
New does no network I/O.The application builds a camera to draw its page even when the camera is off.
Controls() and Page() do not change for a given configuration.The application reads them once, when it builds the camera.
Set validates the value before sending anything.An invalid value never reaches the camera. The application checks it too, before calling the module.
Connect reports the outcome with a Status event, then keeps reconnecting until Close.The application waits for that first status to tell the user whether the camera answers.
Every change the camera reports is emitted.The window and the panel show what the camera really did, not what was asked.
Errors are the SDK errors (see Errors).The window shows them without knowing the brand.
More info: one call at a time

The application never calls a module concurrently. A user action, a WebSocket message, a timer: each is delivered as one call, and the next waits until it returns. Module code therefore needs no locks and no goroutines; it reacts to calls and callbacks. Keep each call short: a call that runs longer than the call timeout (10 seconds) stops the module.

Calls that wait on the network (HTTP, OpenWebSocket) block the module while they run, which is fine: each request has its own short timeout.

Camera lifecycle

  1. At start-up the application loads each file of the modules folder, reads its declaration and checks it.
  2. The user assigns a camera to a button. The application validates the entry (name, address, port, credentials) and starts a fresh instance of the module for this camera: two cameras of the same model share nothing.
  3. The application connects. The module reports "connected" and the status dot turns green.
  4. The user asks for f/1.4. The application checks the value against the declared limits, then passes it to the module.
  5. The module emits the real value (here f/2.8, the lens limit). The window and the panel show it.

Walkthrough: the demo module

modules/demo simulates a studio camera with a 24–70 mm f/2.8 zoom. It has no network address: it lets anyone try the application and the panel without a camera. It is the reference to copy.

1. The program and the declaration

package main

import "github.com/valentindoche/rcp-for-all-camera/sdk/rcpmod"

func main() {}                              // stays empty
func init() { rcpmod.Register(module{}) }  // plugs the module in

type module struct{}

func (module) Info() rcpmod.Info {
    return rcpmod.Info{
        ID: "demo", Brand: "Demo", Name: "Demo camera",
        Transports: []string{rcpmod.TransportEthernet},
        Auth:       rcpmod.AuthNone,         // no credentials
        Support:    rcpmod.SupportSupported,
        NoAddress:  true,                   // no address to enter
        InterchangeableLens: true,          // offers the "power zoom" option
    }
}

2. The controls

Each control is a description built with the SDK helpers. A standard id is enough: the application adds the label and the section shown on screen.

func specs() []rcpmod.ControlSpec {
    return []rcpmod.ControlSpec{
        rcpmod.Range(rcpmod.Iris, 1, 22, 0.1, "f"),                    // f/1 to f/22
        rcpmod.Action(rcpmod.AutoIris),                                   // an "auto" button
        rcpmod.Range(rcpmod.Gain, -12, 36, 2, "dB"),                    // 2 dB steps
        rcpmod.Enum(rcpmod.ISO, rcpmod.Opts("400", "800", "1600")),       // a choice list
        rcpmod.Toggle(rcpmod.Record),                                     // on/off
    }
}

3. The camera

func (module) New(cfg rcpmod.Config, host rcpmod.Host) (rcpmod.Camera, error) {
    s := rcpmod.NewSpecs(specs())
    if !cfg.PowerZoom {
        s = s.Without(rcpmod.Zoom)          // no zoom without a power zoom lens
    }
    return &camera{host: host, specs: s, vals: initial()}, nil
}

func (c *camera) Connect() error {
    c.on = true
    c.host.Emit(rcpmod.StatusEvent(rcpmod.StateConnected, ""))   // nothing to reach
    return nil
}

func (c *camera) Set(id string, v rcpmod.Value) error {
    if _, err := c.specs.Validate(id, v); err != nil {
        return err                               // refused before anything else
    }
    if !c.on {
        return rcpmod.ErrNotConnected
    }
    for _, e := range c.apply(id, v) {          // the iris stays inside the lens, etc.
        c.host.Emit(e)
    }
    return nil
}

Behave like a real camera. The demo applies the consequences of each setting: the iris stays between f/2.8 and f/22, shutter speed and angle follow each other, auto white balance settles on 5600 K. A module should do the same: emit what the camera actually did.

More info: a real network camera

modules/bm-studio-6k-pro controls a Blackmagic Studio Camera 6K Pro over its REST API. It shows the patterns a network module needs:

  • Connect opens the camera's event WebSocket and subscribes; the camera answers with every current value, and the module reports "connected" when both subscriptions are answered.
  • On a dropped socket it reports "disconnected" and schedules a reconnection with host.After, with a growing delay (1 s up to 10 s).
  • Set sends one PUT; the new value comes back as a socket event, which updates the cache and is emitted.
  • Everything read from the network is checked before use: finite numbers, known shapes.

The UI file: ui.go

Every module has a ui.go file that lays out its camera page. The page is rows of blocks, top to bottom; the blocks of a row share its width equally. A block is a standard card (iris, gain, color wheel…), a panel of controls with the widget of your choice, a grid of other blocks, or "the remaining controls".

// modules/demo/ui.go
func (c *camera) Page() rcpmod.Page {
    return rcpmod.StandardPage().AddRow(      // the generic page, plus one row
        rcpmod.Controls("Demo", 2,                   // a titled panel, two columns
            rcpmod.With(tallyLamp, rcpmod.WidgetSwitch),
            rcpmod.With(tallyTest, rcpmod.WidgetButton),
            rcpmod.With(firmware, rcpmod.WidgetReadout),
            rcpmod.With(cameraID, rcpmod.WidgetText),
        ),
    )
}

The generic page

rcpmod.StandardPage() is the page every standard camera gets: the exposure half (iris, lens, gain, shutter, ND, white balance, image cards and presets) and the color half (the three wheels and every other control, by section). Return it as is when it suits your camera, or start from it:

func (c *camera) Page() rcpmod.Page { return rcpmod.StandardPage() }

Or describe the page yourself, block by block. A PTZ camera without color correction could use:

rcpmod.Page{}.
    AddRow(rcpmod.Card(rcpmod.BlockIris), rcpmod.Card(rcpmod.BlockLens), rcpmod.Card(rcpmod.BlockGain)).
    AddRow(rcpmod.Controls("Pan / tilt", 2, rcpmod.Show(rcpmod.Pan), rcpmod.Show(rcpmod.Tilt),
        rcpmod.With(rcpmod.PresetRecall, rcpmod.WidgetButtons))).
    AddRow(rcpmod.Remaining())

Rules

RuleWhy
The page only shows controls the camera declares, with widgets that fit their kind.The application checks the page when it builds the camera, and refuses a camera whose page is wrong (the contract suite catches it first).
A standard card whose controls the camera lacks is shown greyed.The layout stays stable across camera models.
Put Remaining() somewhere unless the page shows every control.A control the page does not show cannot be reached from the window. StandardPage already includes it.

More info: how the page reaches the window

The camera implements rcpmod.Designer (a Page() method); a camera that does not gets StandardPage. A planned module passes a Page function to rcpmod.Planned. The application reads the page once, when it builds the camera, converts it and checks it against the controls. The window then builds the page block by block; values and events update every block live.

Testing

A module is ordinary Go code: test it with go test, without WebAssembly and without a camera. sdk/rcpmod/rcpmodtest provides a test host that plays the application.

func TestContract(t *testing.T) { rcpmodtest.Module(t, module{}) }

func TestIrisStaysInsideTheLens(t *testing.T) {
    host := rcpmodtest.NewHost()
    cam := host.Connected(t, module{}, rcpmod.Config{Model: "demo"})
    _ = cam.Set(rcpmod.Iris, rcpmod.Number(1.4))
    if got, _ := host.Last(rcpmod.Iris); got.Number != 2.8 {
        t.Errorf("iris = f/%g, want f/2.8", got.Number)
    }
}
Test hostUse
HTTPHandlerAnswers the module's HTTP requests, like the camera would.
WSHandlerAccepts or refuses a WebSocket (simulate an unreachable camera).
Socket(path), .Push(msg), .Drop(err), .SentDrive an open socket: deliver a camera message, cut the link, read what the module sent.
Advance(d), Pending()Move the virtual clock and run due timers: reconnection tests take no real time.
Events(), Last(id), Status(), Lens(), Logs()Check what the module emitted and logged.
Connected(t, module, cfg)Builds and connects a camera, failing the test if it does not report "connected".

Two contract suites run on every module:

  • rcpmodtest.Module(t, m): the declaration is well formed, every control description is valid and declared once, an unknown control or a value of the wrong kind is refused, with and without a power zoom.
  • rcpmodtest.Online(t, camera): once connected, every readable control answers with a value of its kind.
More info: end-to-end and hardware tests

The application's own tests build the real .wasm files, load them in the module host and run the application-side contract on them, over a real local network against a fake camera (internal/plugins). Run everything with go test ./....

A module that controls a real camera may also have hardware tests, skipped unless an environment variable gives the camera's address. They write values: run them only with the owner's permission, and never on a camera in production.

The sandbox

A module cannot do anything by itself: no file, no network connection, no other program. It only has the services above, and the application limits them. Each limit is checked by a test against a deliberately hostile module; the known vulnerabilities page lists them.

LimitEffect
Network only to the address and port entered for the camera.A module cannot reach the Internet, scan the local network or contact another camera.
No file system, no environment variables.Your documents and settings are out of reach. A camera's password is given to its own module only.
64 MiB of memory per camera, 1 MiB per message, 10 s per call.A module that hangs or grows is stopped; its camera shows an error.

Appendix: the ABI, for other languages

The Go SDK hides everything below. A module written in another language that compiles to WebAssembly (Rust, Zig, C) implements it directly. A module is a WASI preview 1 reactor: it exports _initialize, which the host runs once. Every message is UTF-8 JSON.

DirectionFunctionRole
exportrcp_alloc(len i32) → ptr i32Reserves len bytes the host writes a request into.
exportrcp_call(ptr i32, len i32) → i64Handles one request; returns ptr << 32 | len of the response, valid until the next call.
importrcp.call(ptr i32, len i32) → i64Asks the host for a service; returns id << 32 | len of the answer, which the host keeps.
importrcp.take(id i32, ptr i32)Copies that answer to ptr, where the module reserved len bytes.
importrcp.log(level i32, ptr i32, len i32)Writes a log line (levels −4 debug, 0 info, 4 warn, 8 error).
More info: requests, services and errors

Requests (host to module, field op): info; new with config; controls; page (the page of ui.go, or the standard page); connect; close; get with id; set with id and value; wsMessage with socket and text; wsClosed with socket and error; timer with timer. The response is {"result": …}, {"error": {"code": …, "message": …}}, or {}.

Services (module to host): http with method, path, body (base64); wsOpen with path; wsSend with socket, text; wsClose with socket; after with ms; cancel with timer; emit with event. The answer carries status, body, socket, timer or error.

Error codes: UNKNOWN_CONTROL, INVALID_VALUE, READ_ONLY, NOT_CONNECTED, NOT_IMPLEMENTED, INTERNAL.

The host never calls into the module while the module waits in rcp.call: that is why answers are fetched with rcp.take. The exact fields are defined in sdk/rcpmod/wire_protocol.go and sdk/rcpmod/wire_types.go.

Frequently asked questions

Is WebAssembly fast enough?

A call into a module takes about 10 microseconds; the panel's iris lever sends a value every 50 milliseconds.

Why is a module file about 4.5 MB?

Each file carries the Go runtime, so that modules stay fully independent. The application compiles each file once and caches the result.

How do I update a module?

Replace its file and restart the application. Cameras keep their settings as long as the module id stays the same.

My camera has two ways to set the iris. Which one do I declare?

The one people see, iris, in f-stops. If the camera also accepts a position over the lens' range, declare it as irisNorm with Hidden: the panel's lever uses it.

Where do I put a setting only my camera has?

Declare it with a brand-prefixed id, a label and a group, and show it in a Controls panel of your ui.go, or let the remaining block show it.
